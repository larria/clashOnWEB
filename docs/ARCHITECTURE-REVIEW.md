# 架构评估 — 面向持续卡牌迭代的可扩展性审查

> 评估对象:v0.6.7(47 张卡:27 部队 / 10 建筑 / 10 法术)
> 评估基准:
> - 规格基准:`THIRD-PARTY-SPEC.md`(ClashRoyaleAi C++ / Crash-Loyal Unity 提炼)
> - 迭代基准:剩余 67 张未实装卡(TODO.md 清单),对照 `docs/cards-wiki/` 113 份官方数据
> - 对照实现:ClashRoyaleAi 的 CardRegistry/CardStats/CardFactories 三层(120+ 卡全量注册,含进化/冠军/英雄机制)
>
> 结论先行:**架构方向正确、核心战斗层质量高,不需要推倒重构;但有 5 处结构性债务会在
> 迭代到特定卡牌批次时集中爆发,应分批偿还而非等待**。逐项论证如下。

---

## 一、总体判断

### 1.1 与参考架构的形态对比

| 维度 | ClashRoyaleAi (C++) | 本项目 (JS) | 评价 |
|---|---|---|---|
| 卡牌数据 | CardStats 结构体 + CardRegistry 工厂注册 | cards.js 纯数据对象字面量 | **本项目更轻**,数据/逻辑分离同等干净 |
| 能力表达 | ~60 个 CombatEntity 字段 + 40 个效果类 | `special: {键:参数}` 22 个键 | 等价;JS 数据驱动写法更省 |
| 机制挂钩点 | applyCardMetadata 一次性灌字段 | 5 个解释函数(tickPeriodic/applyDeath/afterAttack/…) | 等价;本项目挂钩点更少更集中 |
| 引擎硬编码卡名 | 无(全数据) | 引擎层无(仅渲染层 8 处 cardId 分支,见 §3.4) | **达标** |
| 确定性/重放 | tick 制 + deepCopy | dt 制 + 固定步长重放(tools/replay.mjs) | 等价(本项目 1/30 固定步长) |

### 1.2 规格吻合度(经 v0.6.7 对齐后的状态)

v0.6.7 已修复 7 处与规格的不一致。当前**未对齐项仅剩 2 类**:

1. **已记录的有意分歧**(不修):塔索敌脚印半径(3.3/4.4 拟合值 vs 纯中心距,<0.5 格);
   tiebreak 绝对血量 vs 百分比。均为 C++ 项目自己也标注的近似选择。
2. **结构性缺失**(与"完整游戏规格"的差距,即本报告主题):投射物系统、位移机制、
   治疗系、持续状态框架、冠军技能等——这些不是 bug,是 67 张待实装卡**需要而当前没有**
   的机制底盘。详见 §2。

### 1.3 核心结论

- **战斗内核(寻路/索敌/攻击/碰撞)不需要重构**。v0.6.x 连续多轮用户战报验证 +
  规格对齐 review,该层已与最成熟的 C++ 实现逐项一致。任何"推倒重来"都会丢弃
  这份验证过的正确性。
- **数据驱动骨架不需要重构**。新卡 = 1 条数据 + 0~1 个能力键,该 SOP 已被
  冰法师/毒药/三火枪/飞桶 4 张迭代零核心改动落地验证。
- **需要的是机制底盘补建**(§2 的 P0/P1)——这是"增量扩展",每项都有 C++ 参考
  实现可对照,不是重构。

以 ReleaseDate 顺序推演剩余 67 张卡,每个机制第一次"被迫需要"的时点:

### P0 — 2016-05-03 批次(下一批)就会撞上

| 缺口 | 触发卡牌 | 现状 | 参考实现 |
|---|---|---|---|

### P2 — 后期机制(可再等)

冠军主动技能(技能按钮+冷却)、王塔驻军、进化卡、哥布林钻机地下层、
地狱飞龙 grace period ramp、电磁炮 resetCooldownOnFreeze 等。
C++ 全部有字段级参考,**不构成架构风险,只构成工作量**。

**爆发风险结论**:P0 三项在接下来 2~3 个批次内必须落地。它们都是"加一层"而不是
"改一层":投射物是新实体类型、位移是 Entity 工具函数、状态框架是字段归并——
均不与现有战斗内核冲突。

## 三、结构性债务(即使不重构也应偿还)

### 3.1 单位与塔的双轨制(P0,建议下一批前处理)

`Tower` 类(tower.js,52 行)与 `Unit`(unit.js)完全平行:索敌两份
(findTowerTarget/findTarget)、攻击循环两份(updateTowers/updateUnits)、
冷却/减速/狂暴字段两份。v0.6.7 的"冷却暂停"修复就被迫改了两处。

- **代价**:每个新状态机制都要写两遍,漏一处就是塔/单位行为分叉(历史上
  "公主塔攻击不到刚过河单位" bug 正是这类分叉)。
- **建议**:让 Tower 复用 Unit 的索敌/攻击判定(塔 = speed 0 + 不动 +
  activated 门控的特殊单位),保留独立字段但共用判定函数。**这是清单里唯一
  有重构性质的项,建议在做投射物系统时顺手完成**(投射物天然要同时打单位与塔)。
- C++ 对照:Tower 继承 Building 继承 CombatEntity,攻击/索敌全在基类——
  双轨正是它没有的问题。

### 3.2 状态字段散置(P1)

frozen/stunned/slowTimer/rageTimer/slowFactor/charged/rampMult/…直接挂在
unit 实例上,读取方(get speed/hitSpeed/currentDmg/canAct)各自组合判断。
治疗系、诅咒系(伤害加深)、无敌帧进来后,这个模式会把"状态交互规则"
(冰冻是否打断冲锋?诅咒是否穿透护盾?)散到每个 getter 里。

- C++ 对照:所有状态计时器在 update() 顶部**一个递减块**统一处理,
  伤害管线在 takeDamage **一个函数**里定序(免疫→诅咒→招架→护盾→扣血)。
- **建议**:新增状态时按 C++ 模式集中——(a) updateUnits 顶部统一计时器
  递减区已接近这个形态,保持;(b) dealDamage 扩展为完整伤害管线
  (现在只有护盾一段);(c) 每个新状态先问"C++ 对应字段是什么、
  在哪个统一块里处理",对齐后再实装。

### 3.3 AI 的 COUNTERS/ROLE 硬编码表(P1,随卡线性劣化)

ai.js 的 `COUNTERS`(卡→应对卡映射)和 `ROLE`(卡→角色分类)是 cardId 白名单。
46 张时 8 张/批的迭代节奏还能手工维护;67 张后 AI "认识新卡"要改两张表,
漏改 = AI 把骷髅军团当坦克用(有 getRole 兜底不会崩,但决策质量劣化)。

- **建议**:转向元数据驱动——卡牌数据加 `aiHints` 字段(role 由
  kind/targets/dmg/range/count 派生,counter 关系按"对空对地/群伤/单体/
  建筑"匹配规则计算)。C++ HeuristicOpponent 甚至不做 counter,只做
  "最贵可负担卡打威胁位"——说明**简单启发式也能接受**,不必追求表的全。
- **时机**:2016-05-03 批次后、累计超 60 张卡前做一次。

### 3.4 渲染层 cardId 分支(低优先级,可容忍)

renderer.js 8 处、graphics.js 2 处 `cardId === 'fireball'` 式分支
(法术特效视觉/护盾颜色)。渲染层按卡定制视觉是合理的,量小(10 处)
且不影响游戏逻辑正确性。**建议**:接受现状,新卡特效优先写成
`effect + color + radius` 参数化(现有 spell 特效已参数化,部分老代码没跟上)。

### 3.5 规格文档维护责任(流程项)

THIRD-PARTY-SPEC.md 的价值在于"实装新机制前先查规格"。建议把
"新机制实装前对照 THIRD-PARTY-SPEC.md 对应章节"写进 ARCHITECTURE-CARDS.md
的 SOP 检查单第 2 步(已顺手补上,见文末)。

## 四、被证伪的候选重构理由(为什么不动)

逐条排除掉的重构选项,防止未来反复:

1. **"改用 ECS/组件化重构"** — 反对。本项目 special 键系统在表达力上与
   C++ 的"60 字段 + 效果类"等价,而规模(2647 行 game 层)远未到需要
   ECS 解耦的复杂度。C++ 参考实现也不用 ECS,用的是继承 + 字段灌装,
   且其规模(120+ 卡)证明了这条路在完整游戏规模下成立。
2. **"tick 制替换 dt 制"** — 反对。dt 制 + 固定步长重放已满足确定性
   (对局记录/场景测试/评测全依赖它且稳定),改 tick 制是纯成本。
3. **"引入游戏引擎/物理库"** — 反对。零依赖是本项目部署前提
   (GitHub Pages 静态托管),且现有碰撞/寻路性能余量充足
   (44 单位 0.36ms/帧)。
4. **"combat.js 拆分"** — 反对。518 行内聚于"移动/索敌/攻击"一个关注点,
   拆开反而增加跨文件跳转。等投射物系统落地时它自然会瘦
   (攻击结算部分迁入 projectile)。

## 五、行动路线图(结论)

按"先修地基、再上批次"排序,每项都有 C++ 参考文件可对照:

| 阶段 | 内容 | 性质 | 对应缺口 |
|---|---|---|---|
| **批次前(2016-05-03 前)** | ① 统一伤害管线(dealDamage 定序化)② 状态计时器集中化(补齐 update 顶部统一递减)③ Tower/Unit 共用索敌攻击判定 | 偿债 | §3.1/3.2 |
| **下一批(2016-05-03)** | 火精灵/熔炉用现有键即可;皇家卫队=shield(已有);熔岩猎犬=多体死亡分裂(summonOnDeath 已有)+空军坦克;矿工=deployZone:'anywhere';电磁炮需 **resetCooldownOnFreeze** 状态(小) | 常规 | — |
| **投射物系统** | 独立 Projectile 实体(追踪/on-hit 随弹/命中吸附),远程攻击结算迁入;矿工/哥布林钻机的"飞行落地"复用 | **机制底盘** | §2 P0 |
| **位移四件套** | pullToward/pushAway/pushAlong + 建筑免疫统一;为渔夫/龙卷风/滚木备 | **机制底盘** | §2 P0 |
| **治疗+变形** | heal(带上限)+ transform(hp 阈值触发换卡);为治疗系/巫婆/加农炮车备 | **机制底盘** | §2 P1 |
| **AI 元数据化** | role 派生 + counter 规则化,替换两张硬编码表 | 偿债 | §3.3 |

估算:三个机制底盘各约 100~200 行 + 场景测试,均有 C++ 逐行参照,风险低。
全部完成后,剩余 67 张卡里的 ~55 张可回归"纯数据 + 既有键"实装,
只有冠军技能/王塔驻军/进化等 P2 机制需要新底盘。
